# 智膳校园外卖点餐系统------后端需求与设计说明

**项目名称：** 智膳校园外卖点餐系统\
**文档版本：** v1.0

## 1. 文档说明

本文档整理系统后端需要实现的业务功能、接口、数据存储和关键处理规则，作为后端编码、联调和测试的依据。

系统面向校园单商家点餐场景。后端负责用户身份认证、业务数据处理、订单与库存管理，以及管理端权限校验。系统采用前后端分离方式，前端通过
HTTP 接口访问后端服务。

## 2. 技术方案

  层次       技术                  用途
  ---------- --------------------- ------------------------------------
  运行环境   Java 21               后端开发语言及运行环境
  后端框架   Spring Boot 4.1.2     提供接口和业务服务
  数据访问   MyBatis-Plus          数据库查询、更新和分页
  数据库     MySQL 8               保存账号、菜品、购物车和订单等数据
  身份认证   JWT（jjwt）及拦截器   识别登录用户并控制接口访问

项目以单机部署和毕业设计演示为主要目标，暂不引入
Redis、消息队列和微服务。Java 21 与 Spring Boot 4.1.2
的版本组合应在项目启动前完成构建验证，并锁定依赖版本。

  BE-DISH-02        分类管理          支持新增、修改、删除和调整分类顺序                   P0

  BE-DISH-03        菜品查询          支持按分类、关键词查询菜品；用户端只返回已上架菜品   P0

  BE-DISH-04        菜品管理          维护名称、价格、分类、描述、辣度、库存和上下架状态   P0

### 3.4 订单与库存

  ------------------------------------------------------------------------------------------------------------------
  编号              功能              后端处理要求                                                 优先级
  ----------------- ----------------- ------------------------------------------------------------ -----------------
  BE-ORD-01         创建订单          校验购物车、菜品状态、库存和数量；由后端计算金额并生成订单   P0

  BE-ORD-02         模拟支付          用户确认模拟支付后，将订单状态更新为制作中                   P0

  BE-ORD-03         订单列表          分页查询当前登录用户的订单                                   P0

  BE-ORD-04         订单详情          返回订单金额、状态、收货信息和菜品明细                       P0

  BE-ORD-05         取消订单          按订单状态判断能否取消；符合条件时恢复库存                   P0

  BE-ORD-06         管理订单          管理员查询全部订单，并按规定的状态流转规则处理订单           P0

  BE-ORD-07         经营统计          统计当日订单数量和营业额                                     P1

订单列表、详情和取消接口必须根据当前登录用户限制数据范围，不能仅凭客户端传入的订单
ID 操作数据。

订单主表保存下单时的收货地址快照；订单明细保存菜品名称、单价和数量。菜品改名、改价或用户修改地址后，已生成订单中的历史信息不应发生变化。订单金额必须根据数据库中的菜品价格计算，不能直接使用前端传入的总金额。

### 3.5 全局处理

  ----------------------------------------------------------------------------------------------------
  编号              功能              后端处理要求                                   优先级
  ----------------- ----------------- ---------------------------------------------- -----------------
  BE-COM-01         统一响应          JSON 接口使用统一响应结构                      P1

  BE-COM-02         异常处理          统一处理常见异常，并返回前端可识别的错误信息   P1

  BE-COM-03         分页              列表接口支持分页，每页最多返回 20 条记录       P0

建议统一响应格式如下：

``` json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

`code` 表示业务处理结果，`message` 用于说明处理情况，`data`
保存返回数据。分页接口可在 `data` 中包含记录列表、总数和分页信息。

## 5. 核心业务规则

### 5.1 创建订单

后端按以下顺序处理订单：

1.  检查用户登录状态和请求参数。
2.  检查购物车是否为空。
3.  查询购物车中的菜品，确认菜品仍处于上架状态。
4.  校验每种菜品的库存和购买数量。
5.  使用数据库中的实际价格计算订单金额。
6.  创建订单主表和订单明细，并保存菜品及收货地址快照。
7.  扣减库存，相关数据写入放在同一事务中。
8.  事务提交成功后，清空本次已结算的购物车项目。
9.  用户确认模拟支付后，将订单状态改为"制作中"。

如果校验失败或库存扣减失败，应回滚本次事务并向用户说明原因。购物车不能在事务提交前清空。

库存扣减应使用带条件的原子更新：

``` sql
UPDATE dish
SET stock = stock - #{quantity}
WHERE id = #{id}
  AND status = 1
  AND stock >= #{quantity};
```

如果受影响行数为
0，说明菜品不存在、已下架或库存不足，本次下单不能继续。多菜品订单中，只要有一项扣减失败，就应回滚整笔订单及此前已执行的库存更新。

同一次下单请求重复到达时，应通过幂等控制返回原有处理结果，避免重复生成订单。

### 5.2 订单状态

  状态值   状态名称   含义
  -------- ---------- --------------------------------
  0        待支付     订单已创建，尚未完成模拟支付
  1        制作中     模拟支付成功，商家正在准备餐品
  2        配送中     进入配送环节
  3        已完成     订单流程结束
  4        已取消     订单已取消

状态变化规则：

``` text
待支付 ──→ 制作中 ──→ 配送中 ──→ 已完成
   │
   └──→ 已取消

制作中 ──→ 已取消
```

-   待支付订单可以取消；制作中订单也允许取消，具体按系统设定的业务规则处理。
-   配送中和已完成订单不能直接取消。
-   已取消订单不能再次进入其他状态。
-   管理员只能执行规定的状态转换，不能跳过中间状态。
-   每次状态变化都应记录时间。
-   取消订单和恢复库存必须在事务中完成，并校验订单当前状态，避免重复取消造成库存重复增加。

## 6. 数据库设计

系统使用 MySQL 8，主要包含以下 8 张业务表。除特别说明外，各表使用
`BIGINT` 自增主键 `id`，并记录创建时间 `created_at`。

  ------------------------------------------------------------------------------------------------------------------------------------------
  表名                    主要字段                                                                                 用途
  ----------------------- ---------------------------------------------------------------------------------------- -------------------------
  `user`                  `username`、`password`、`phone`、`role`                                                  用户账号和角色

  `address`               `user_id`、`receiver`、`phone`、`building`、`room`                                       用户收货地址

  `category`              `name`、`sort`                                                                           菜品分类及排序

  `dish`                  `category_id`、`name`、`price`、`description`、`image_url`、`spicy`、`stock`、`status`   菜品信息

  `cart_item`             `user_id`、`dish_id`、`quantity`                                                         购物车项目

  `orders`                `order_no`、`user_id`、`status`、`total_amount`、`address_snapshot`                      订单基本信息

  `order_item`            `order_id`、`dish_id`、`dish_name`、`price`、`quantity`                                  订单菜品明细

  `shop_status`           `id`、`status`、`updated_at`                                                             店铺营业状态，单行表，1
                                                                                                                   表示营业、0 表示休息
  ------------------------------------------------------------------------------------------------------------------------------------------

字段和约束要求：

-   `username` 设置唯一约束，密码使用 BCrypt 哈希后保存。
-   `role` 区分普通用户和管理员，例如 0 为普通用户、1 为管理员。
-   `dish.price` 使用 `DECIMAL(10,2)`，不使用浮点数保存金额。
-   `dish.spicy` 取值为 0～3，表示辣度等级。
-   `dish.status` 区分上架和下架。
-   `cart_item` 设置 `(user_id, dish_id)` 联合唯一约束。
-   `orders.order_no` 设置唯一约束。

建议为 `orders(user_id)` 和 `order_item(order_id)`
建立索引。若需要按订单创建时间分页查询，可进一步评估
`(user_id, created_at)` 联合索引。

## 7. 非功能要求

-   列表接口支持分页，每页最多返回 20 条记录。
-   并发下单时不能发生库存超卖，应使用数据库条件更新和事务保证库存一致性。
-   核心演示流程连续执行 3 次，应能正常完成，且不出现影响业务的异常。
-   管理端接口必须校验管理员身份。
-   用户不能查询或操作其他用户的订单和地址。

## 8. 后端测试重点

  测试场景                     预期结果
  ---------------------------- --------------------------------
  用户名重复注册               注册失败并返回明确提示
  空购物车创建订单             拒绝提交
  库存不足时下单               提示缺货菜品，不产生不完整订单
  同一请求重复提交             不重复创建订单
  菜品已下架但仍在购物车       结算失败并提示原因
  取消已完成订单               拒绝操作
  未登录访问受保护接口         返回未认证错误
  普通用户访问管理接口         拒绝访问
  查询其他用户的订单           不返回对方订单数据
  修改菜品价格后查看历史订单   保留下单时的价格
  并发购买最后一份菜品         最多一次扣减成功，不出现负库存

## 9. 开发阶段与交付内容

### 第一阶段：核心业务（4～6 周）

完成后端基础配置、数据库设计、账号认证、菜品分类、购物车、订单、库存和模拟支付。

阶段验收时，应能通过接口完成注册、登录、菜品查询、购物车操作、创建订单和模拟支付；管理员能够推进订单状态，用户能够查询订单状态。

### 第二阶段：功能完善（3～4 周）

完善地址、店铺营业状态、经营统计、图片管理、统一异常处理和接口联调，并完成库存并发测试。

### 第三阶段：测试与整理（2 周）

完成核心业务回归测试，整理数据库设计、接口说明、测试记录和毕业设计所需材料。
